# 产品交付基线与未完成项

用户要求产品级交付、共同硬件同步与尽可能高的速度。当前固件是 0.5.0 开发版本，**不具备产品放行结论**。编译通过与合成回归通过不等于实物验收。

## 产品目标草案

现阶段优先争取原生双目 1280×800@120 采集、320×200 双目/深度 USB 请求 60Hz、有效视觉更新尽可能接近采集速度。稠密深度频率可独立配置以比较 CPU 成本；当前开发配置为 30Hz。实际能达到的工作点、延迟、深度/轨迹精度、温度和连续运行门槛需要目标板数据与用户验收要求共同确定，不能把请求值写成保证指标。

相机必须共用硬件触发，IMU 必须关联同一硬件事件并有可测时间误差预算。PWM→FSIN + DEN 标记方案见 `hardware-sync.md`，尚未应用；DEN 本身不保证 ADC 锁相。如果要求固定采样相位，应优先评估以 IMU 的脉冲 DRDY 为时钟，硬件分频后触发左右相机：例如标称 416Hz 的 IMU /4 得到标称 104Hz 相机触发，SPI 读取和 Linux 调度不参与触发时刻。分频器需受控复位、门控与整形，并校准 DRDY 到有效 IMU 测量及相机曝光的固定延迟；器件、线路与驱动均需落地验证后才能选为正式设计。不能用 Linux IRQ 内的软件 GPIO 翻转冒充硬件分频。

## 操作系统的实际状态

Buildroot 用于构建根文件系统，默认内核现为本工程移植的 `5.10.160-rt77-mohism`，启用 `CONFIG_PREEMPT_RT=y` 和 `CONFIG_HZ=1000`。完整补丁、源码哈希校验、ARM 构建及 IMU 模块 ABI 检查已接入工程。普通内核保留为单独的回退构建。详见 [实时内核](realtime.md)。

编译通过不能证明实时性达标。还需要在相机、深度、USB 双 ACM 满负载下测量调度和 IRQ 延迟，并检查厂商驱动的睡眠上下文、优先级继承和长期稳定性。后续 Wi-Fi、编码驱动也要针对 RT 内核重新构建和验证。单独跑空载 cyclictest 或设置 SCHED_FIFO 不构成产品实时性结论，硬件触发链路仍独立于调度策略。
